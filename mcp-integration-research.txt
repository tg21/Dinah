Codex / Claude / Gemini / OpenCode

There isn't one universal --tools ... protocol shared by these CLIs.

Some support MCP configuration through CLI flags/config files/environment variables; others expect MCP servers to be registered in their own configuration. So you generally need a thin adapter per harness.

For example, conceptually:

switch (agent.harness) {
  case "codex":
    return spawnCodex(agent, resolveMcp(agent.tools));

  case "claude":
    return spawnClaude(agent, resolveMcp(agent.tools));

  case "gemini":
    return spawnGemini(agent, resolveMcp(agent.tools));

  case "opencode":
    return spawnOpenCode(agent, resolveMcp(agent.tools));
}

The MCP servers themselves don't need to be duplicated.

After the agent exits, delete the temporary configuration.

Even better: distinguish MCP servers from MCP tools

 └── MCP server: filesystem
        ├── read_file           ✓
        ├── write_file          ✗
        └── delete_file         ✗

That's much safer than simply saying "this agent has GitHub."

For the architecture you described, I'd look at these:
1. Pharos — probably closest to what you're asking for

positions itself as an MCP package manager/CLI, not merely a directory.

It can:

    Search across multiple MCP registries
    Install MCPs
    Verify packages
    Manage versions/lockfiles
    Generate/update client configuration
    Connect to multiple MCP clients

For example, its model is roughly:

pharos search postgres
pharos install <mcp>

It currently aggregates the official registry, Glama, Smithery, mcp.so, mcp.directory, and others.

For your Node.js orchestrator, this is particularly interesting.

│   └── slack/

├── mcp-registry.json
└── orchestrator.js

and let your infrastructure manage MCP installation independently of Codex/Claude/Gemini/OpenCode.
